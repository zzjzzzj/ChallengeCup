## 3. 系统总体架构

### 3.1 当前推荐部署链路

当前已形成结果并用于部署说明的是“三模型互斥路由”。每张图先经过场景分类器，然后只执行一个检测分支：

```text
                  图像 + 可选传感器提示
                           │
                           ▼
             场景认知模型：YOLOv8n-cls 224
                 输出 scene_id, scene_conf
                           │
             ┌─────────────┴─────────────┐
             │                           │
       air / sea                    forest / urban
       conf >= 0.60                或 conf < 0.60
             │                           │
             ▼                           ▼
   easy 六分类 YOLOv10n          hard 三分类 YOLOv8n
       输入 640×640                   输入 960×960
             │                           │
             └─────────────┬─────────────┘
                           ▼
                统一六分类检测结果 JSON
                           │
                           ▼
                 一致性诊断、耗时记录、反馈 replay
```

路由器只决定检测分支，不修改检测框，也不使用验证集标签替换模型预测。低置信度样本进入 `hard` 分支，以计算开销换取困难场景下更稳健的目标召回。

### 3.2 训练与持续学习链路

```text
原始四类数据
  → 仅增广 train
  → 训练四类基础模型
  → 原始六类增量数据
  → 仅增广 train
  → 按类别与来源族划分多个小批次
  → 构建容量 200 或 500 的回放池
  → ER 或 DER 逐批训练
  → 可选 Sparse-MoE 特征适配
  → 每批次在 val 上评估和选模
  → 最后一批完成后仅在 test 上评估一次
  → 六类最终模型与持续学习指标
```

### 3.3 两级路由的关系

项目中存在两种不同层级的“路由”，不能混为同一机制：

- 三模型场景路由是模型级粗路由，根据场景在 `easy` 与 `hard` 检测器之间二选一；
- Sparse-MoE 是单个检测模型内部的特征级动态路由，每张图选择 Top-K 专家完成残差适配。

当前三模型 ONNX 部署方案不依赖 Sparse-MoE。是否在未来检测器中同时启用 Sparse-MoE，需要通过消融实验和部署导出验证决定。

## 4. 当前实现边界与关键口径

### 4.1 多模态边界

Agent 接口支持 `ir`、`sar` 和 `unknown` 传感器字段，用于数据记录、上下文监督和策略接口兼容。当前三模型 ONNX 的实际张量输入仍为图像张量，尚未实现雷达与红外的像素级或特征级联合编码。因此：

- 多模态接口支持：已具备；
- 多模态上下文用于 Sparse-MoE 路由：PyTorch 路线已实现；
- 多模态特征融合：尚未完成。

### 4.2 Agent 模型包边界

仓库 `Agent/` 默认仍绑定早期四分类交付包，默认类别及部分 ONNX 输出形状是旧口径。当前三模型六分类部署以以下内容为准：

- `ChallengeCup-agent-soldier-route/route_inference.py`；
- `ChallengeCup-agent-soldier-route/route_3onnx_best_20260829/`。

将三模型包接入 `Agent/` 统一入口时，必须同步更新 `Agent/config.py` 中的类别列表、模型相对路径、输入输出形状和模型清单校验，不能直接复用旧四分类 manifest。

### 4.3 场景类别顺序冲突

两条历史路线记录的场景类别顺序不同：

| 使用场景 | 类别顺序 |
| --- | --- |
| 当前三模型 YOLOv8n-cls ONNX 部署 | `air, forest, sea, urban` |
| 旧 SC/传统路线文档口径 | `air, sea, urban, forest` |

类别名称相同不代表张量索引相同。接入任何场景 checkpoint 时，必须以该 checkpoint 的 `names`、导出配置和实际输出顺序为准，并同步更新路由配置。三模型路由代码中的索引规则只适用于其配套的 `[air, forest, sea, urban]` 模型，不得直接套用到旧顺序。

## 6. 类别体系与数据协议

### 6.1 目标类别

基础阶段为四类，增量完成后固定扩展为六类。类别 ID 和顺序是训练与部署协议的一部分，不允许任意调整。

| ID | 类名 | 阶段 |
| ---: | --- | --- |
| 0 | `soldier` | 基础四类 |
| 1 | `small_aircraft` | 基础四类 |
| 2 | `warship` | 基础四类 |
| 3 | `tank` | 基础四类 |
| 4 | `patrol_boat` | 新增类 |
| 5 | `armored_vehicle` | 新增类 |

四类 checkpoint 的 `names` 必须严格等于前四类及上述顺序；六类数据 YAML 必须包含全部六类且顺序一致。代码按名称完成检测头扩展和旧类权重迁移，错误的名称或顺序会造成训练与推理语义错位，应在启动前阻断。

### 6.2 YOLO 数据目录

基础数据和增量数据均使用以下目录协议：

```text
dataset_root/
├─ data.yaml
├─ images/
│  ├─ train/
│  ├─ val/
│  └─ test/
└─ labels/
   ├─ train/
   ├─ val/
   └─ test/
```

每行检测标签格式为：

```text
class_id x_center y_center width height
```

坐标必须归一化到 `[0,1]`。训练图像文件名建议以 `ir_` 或 `sar_` 开头，便于系统生成模态上下文。历史数据无法改名时，可通过 `--default-modality ir` 或 `--default-modality sar` 设置默认模态，但缺失模态样本将被统一视为该模态。

### 6.3 当前三模型数据统计

六分类增量检测数据当前记录为：

- 训练图像：2828 张；
- 原始验证图像：183 张；
- 验证集不包含训练增广图，也不将验证图回流到训练集。

hard 三分类数据由森林和城市困难场景筛选生成，只保留三类目标：

| split | 图像数 | 标注框数 |
| --- | ---: | ---: |
| train | 1508 | 6652 |

hard 数据集可通过硬链接或复制生成数据副本，标签仅保留三类目标，验证集不包含训练增广图。

### 6.4 场景分类数据

YOLOv8n-cls 场景分类器使用 r1+r2 增量数据，目录遵循 Ultralytics 分类格式：

```text
scene_cls_r1_r2_incremental/
├── train/
│   ├── air/
│   ├── forest/
```

路由评估应回到目标检测的原始验证图上，统计场景误判是否跨越 `easy/hard` 分组；该指标比单独的四分类 Top-1 更符合最终路由任务。

## 7. 三模型结构与接口

### 7.1 场景分类模型

部署文件：`scene_classifier_r1r2_route_safe_224.onnx`

模型采用 YOLOv8n-cls，包含轻量卷积骨干、多级下采样、C2f 特征提取模块和 Classify 分类头。实际 checkpoint 约含 1.44M 参数、10 个主模块层。

| 项目 | 配置 |
| --- | --- |
| 任务 | 四分类图像分类 |
| 部署场景顺序 | `air, forest, sea, urban` |
| 参数量 | 约 1.44M |
| 输入 | `[1,3,224,224]`，RGB、float32 |
| 输出 | `[1,4]` |
| ONNX opset | 12 |
| batch | 1 |
| 作用 | 输出场景标签和路由置信度 |

最高场景概率记为 `scene_confidence`，它与检测框的目标置信度是两个不同概念，不能混用。

### 7.2 easy 六分类检测模型

部署文件：`detector_6class_640.onnx`

模型由四类基础检测模型增量迁移为六类，采用 YOLOv10n。骨干由卷积、SCDown、C2f、SPPF 和 PSA 组成，颈部通过 Upsample、Concat 及 C2f/C2fCIB 进行三尺度融合，末端使用 `v10Detect` 端到端检测头。实际 checkpoint 约含 2.71M 参数、24 个主模块层。

| 项目 | 配置 |
| --- | --- |
| 任务 | 六类目标检测 |
| 参数量 | 约 2.71M |
| 训练尺寸 | 960×960 |
| 部署尺寸 | 640×640 |
| 输入 | `[1,3,640,640]` |
| 输出 | `[1,300,6]` |
| 类别顺序 | `soldier, small_aircraft, warship, tank, patrol_boat, armored_vehicle` |

每个候选按 `[x1,y1,x2,y2,confidence,class_id]` 解析。输出已包含全局六分类编号，不需要额外类别映射。

### 7.3 hard 三分类检测模型

部署文件：`hard_3class_corrected_960.onnx`

模型面向森林和城市中的小目标、遮挡和复杂背景，采用 COCO 预训练 YOLOv8n，包含 C2f、SPPF、PAN/FPN 三尺度融合和标准 `Detect` 头。实际 checkpoint 约含 3.01M 参数、23 个主模块层。

| 项目 | 配置 |
| --- | --- |
| 任务 | 困难陆地场景三类检测 |
| 参数量 | 约 3.01M |
| 输入 | `[1,3,960,960]` |
| 输出 | `[1,7,18900]` |
| 检测头 | YOLOv8 Detect 原始检测头 |
| 局部类别顺序 | `soldier, tank, armored_vehicle` |
| ONNX opset | 12 |

hard 分支输出需要解码、置信度过滤和 class-aware NMS，并将局部类别映射回全局六分类：

| hard 局部 ID | 类别 | 全局 ID |
| ---: | --- | ---: |
| 0 | `soldier` | 0 |
| 1 | `tank` | 3 |
| 2 | `armored_vehicle` | 5 |

### 7.4 仓库保留的其他识别路线

仓库还保留：

1. 手工图像特征 → `StandardScaler` → ANOVA `SelectKBest(k=30)` → RBF-SVM 的传统场景分类路线；
2. 基于真实框裁剪的 ResNet18 目标分类路线。

历史记录中，传统场景分类在 111 张独立测试图上 Accuracy 为 92.79%、Macro-F1 为 92.25%；目标裁剪分类 Accuracy 为 99.79%。前者不是本次 Class-IL 结果，后者不包含定位能力，均不能替代六类目标检测 mAP。

## 8. 场景路由、预处理与后处理

### 8.1 路由规则

三模型配套的 `[air, forest, sea, urban]` 场景模型输出四类概率后，取最高概率：

```python
scene_id = argmax(scene_scores)
scene_confidence = max(scene_scores)
```

路由阈值为 `0.60`：

```python
if scene_confidence < 0.60:
    route = "hard"
elif scene_id in (0, 2):       # air, sea
    route = "easy"
else:                          # forest, urban
    route = "hard"
```

只有高置信度 `air/sea` 进入低分辨率 easy 分支；`forest/urban` 和所有低置信度样本进入高分辨率 hard 分支。

### 8.2 安全回退

低置信度回退到 hard 主要用于保护 `soldier` 召回率。场景模型若在 easy/hard 两组之间犹豫，回退会增加计算量，但可避免把森林或城市小目标交给较低分辨率检测器。

在当前 183 张原始验证图上，route-safe checkpoint 有一张 hard 图的最高场景概率约为 `0.589`，因低于阈值而正确回退到 hard。按最终检测分组统计，easy/hard 有效路由准确率为 100%。

easy 分支保留全部六类输出，避免错误的场景细分类规则屏蔽新增类别；hard 分支通过类别映射保持统一六分类格式。

### 8.3 图像预处理

1. 读取图像，并从 BGR 转为 RGB；
2. 场景分类器保持宽高比，将短边缩放到 224，再做 224×224 中心裁剪；
3. easy/hard 检测器保持宽高比，分别 letterbox 到 640×640 和 960×960，填充值为 114；
4. 转为 NCHW float32，像素归一化到 `[0,1]`；
5. 检测框通过逆 letterbox 恢复到原图坐标；
6. 将坐标裁剪到原图边界。

分类器的“短边缩放 + 中心裁剪”不能替换为检测器 letterbox 或直接拉伸。真实验证图抽查中，该分类预处理下 PyTorch 与 ONNX 四类概率的最大绝对差约为 `9.2e-9`。

### 8.4 两种检测头的后处理差异

- easy YOLOv10 输出端到端候选框，主要执行置信度过滤和坐标还原；
- hard YOLOv8 输出原始检测头张量，需要框解码、类别分数计算、置信度过滤、class-aware NMS 和类别映射。

两条分支不能直接共用完全相同的后处理代码。

### 8.5 端到端伪代码

```python
scene_scores = scene_router(image_224)
scene_id = argmax(scene_scores)
scene_conf = max(scene_scores)

if scene_conf < 0.60 or scene_id in (1, 3):
    raw = hard_detector(letterbox(image, 960, 960))
    detections = decode_yolov8(raw)
    detections = confidence_filter_and_nms(detections)
    detections = remap_hard_ids(detections, {0: 0, 1: 3, 2: 5})
else:
    raw = easy_detector(letterbox(image, 640, 640))
    detections = parse_yolov10_end2end(raw)
    detections = confidence_filter(detections)

return unified_result(scene_id, scene_conf, detections)
```

### 8.6 统一输出

单个检测结果格式：

```json
{
  "class_id": 0,
  "class_name": "soldier",
  "confidence": 0.73,
  "bbox_xyxy": [0, 0, 100, 100]
}
```

完整报告还应包含：

- `scene.label`、`scene.confidence`；
- `final_scene`，低于阈值时标记为 `uncertain`；
- `routing.route`、`routing.reason`；
- 检测器输入尺寸；
- 目标数量、冲突诊断、各阶段与总耗时；
- 模型包路径和 SHA-256 校验结果。

## 9. Agent 推理架构

Agent 负责图像读取与质量分析、模态判断、场景识别、目标检测、可选目标分类、一致性检查、反馈记录和结果格式化。

`Agent/detection.py` 当前检测策略为：

1. 配置的本地 YOLO 权重存在时，使用 Ultralytics 加载并推理；
2. 模型加载或推理失败且允许 fallback 时，读取图像同名 YOLO 标签；
3. 两者均不可用时返回空目标列表并记录 warning。

sidecar 标签回退只用于联调和数据检查，不代表真实模型能力。

当加载 Sparse-MoE 模型时，Agent 可读取并附加以下诊断：

- `expert_ids`：Top-K 专家编号；
- `expert_weights`：归一化路由权重；
- `router_entropy`：路由分布熵；
- 模态和场景辅助预测；
- MoE 配置和当前路由诊断。

结果可输出 JSON 和 UTF-8 BOM CSV，主要 CSV 字段包括：

```text
image, scene, modality, target_type_count, target_total_count,
target_details, max_confidence, description
```

中文 `description` 由确定性格式化代码生成，不依赖在线大语言模型，可在离线环境复现。

## 10. 离线增广与上下文元数据

### 10.1 增广原则

增广工具只扩充 `train`，`val` 和 `test` 只复制原图与原标签，避免评估集包含训练图像变体。默认保留原始训练样本，并为每个样本生成三个独立变体。操作由图像文件名和操作名的 SHA 哈希决定，相同输入与代码版本下结果确定。

### 10.2 IR 与 SAR 操作

IR 样本：

- `ir_gamma_bright`：确定性 gamma，约 `[0.50,0.70]`；
- `invert_255`：灰度/颜色反相；
- `rot180`：旋转 180°。

SAR 样本：

- `rot180`；
- `sar_rot90_cw`：顺时针旋转 90°；
- `sar_gamma`：从 `[0.45,0.68]` 或 `[1.55,1.90]` 确定性取值。

几何变换同步更新 YOLO 框坐标。工具还会校验图片、标签、类别范围、`nc/names` 一致性和重复 basename。

输出包括：

- `data.yaml`；
- `classes.txt`；
- `augmentation_manifest.csv`；
- `augmentation_summary.json`。

输出目录必须不存在或为空。当前实现不提供递归覆盖，以降低误删本机数据的风险。

### 10.3 已增广数据

一键 `four-to-six-yolo` 会先增广基础数据和增量数据。已经增广并完成 train/val/test 划分的数据不能再次直接输入该命令，否则会发生二次增广；应从批次准备与批次训练开始执行。

### 10.4 上下文元数据

批次准备阶段生成上下文索引，典型字段为：

```text
materialized_image_path
source_image
sensor
scene
split
stage
sample_role
augmentation_operation
metadata_source
```

`sample_role` 区分 current、replay、validation 和 test；DER 据此仅在 replay 样本上施加 dark loss。模态优先来自增广 manifest 或显式元数据，缺失时可根据文件名回退；场景缺失则保持 unknown，并在辅助损失中掩码。

## 11. 四类到六类的多批次 Class-IL

### 11.1 问题定义

当前实现面向：

- 起点为已训练的四类检测模型；
- 总类别空间固定扩展为六类；
- 增量数据分多个批次到达；
- 单批次可包含任意非空类别子集；
- 同一类别可跨批次重复出现；
- 每类最多使用 K 个当前来源样本族，以模拟小样本；
- 不保留全部历史数据，仅维护容量为 200 或 500 的回放池；
- 最终使用一个六类头预测全部已见类别，不依赖任务 ID。

因此当前实现属于 Class-Incremental Learning（Class-IL），不是 Task-IL。

### 11.2 固定六类头与权重迁移

从第一批增量训练开始，学生模型即使用固定六类检测头：

```text
旧类 0..3：从四类 checkpoint 按名称复制分类通道
新类 4..5：保留六类检测头的新初始化参数
```

实现不依赖 Ultralytics 内部易变化的 `_remap_cls_by_names`，并处理检测头属性为空、输出尺度变化和 AMP dtype 不一致等边界。初始 checkpoint 必须是可加载的本地 `.pt`，且 `names` 是严格四类前缀。

### 11.3 批次计划

支持两种配置：

1. `--num-batches N`：确定性生成 N 个批次；
2. `--batch-plan plan.json`：显式声明每批允许到达的类别。

推荐使用显式计划：

```json
{
  "batches": [
    {"id": "batch_01", "classes": ["soldier"]},
    {"id": "batch_02", "classes": ["small_aircraft"]},
    {"id": "batch_03", "classes": ["warship"]},
    {"id": "batch_04", "classes": ["tank"]},
    {"id": "batch_05", "classes": ["patrol_boat"]},
    {"id": "batch_06", "classes": ["armored_vehicle"]}
  ]
}
```

也可以将多个类别置于同一批次，或让某类在后续批次再次出现。计划与实际训练集都必须覆盖两个新增类。

### 11.4 来源族隔离与小样本限制

准备器把“原图 + 其全部增广变体”视为一个 source family，并保证整个来源族只进入一个增量批次，防止同源图像跨批泄漏。

`--max-current-images-per-class K` 在来源族层面限制每批每类最多 K 个当前样本，不会把同一原图的多个增广版本误计为多个独立原始样本。

### 11.5 已见类与未来类隔离

每批 YAML 固定为 `nc=6` 和六类 `names`，保证检测头维度不变；训练标签、验证视图和测试视图只暴露截至当前阶段已到达的类别。未来类在首次到达前不进入监督和指标，其结果应记录为 `null`。

## 12. 经验回放、ER 与 DER

### 12.1 回放池

代码当前只接受 200 和 500 两种固定容量。准备阶段可同时生成两套可比实验数据，训练阶段每次选择其中一种。

第一批前，回放池只从基础四类训练集采样。每批完成后，候选集合更新为：

```text
基础四类历史样本 + 截止当前已消费的增量样本
```

随后按已见类别尽量均衡地重建回放池。下一批的 `buffer_before` 必须严格等于上一批的 `buffer_after`，准备器会记录并校验该连续性。

容量统计的是“按类别物化的 replay entry”，不一定等于不同原图数量。多标签原图可为不同类别贡献多个 entry，每个物化标签视图仅保留对应类别标注。分析样本独立性时应按 `source_image` 和 source family 去重。数据物化优先使用硬链接，不支持时回退为复制。

### 12.2 ER

第 `t` 批训练时，ER 将当前数据 `C_t` 与上一阶段回放池 `B_(t-1)` 合并：

```text
D_t = C_t ∪ B_(t-1)
```

模型在混合视图上使用标准 YOLO 监督损失，回放样本持续提供旧类框和类别监督，以减轻灾难性遗忘。

### 12.3 DER

当前 DER 在 ER 数据混合基础上加入冻结教师模型：

- 第一批教师：原始四类 checkpoint；
- 后续批教师：上一批选出的 best checkpoint。

暗知识匹配只作用于 replay 样本，只比较教师已知的旧类别：

```text
L_dark = λ_cls · L_cls_dark + λ_box · L_box_dark
L_total = L_YOLO + λ_DER · L_dark
```

启用 Sparse-MoE 时，其辅助损失继续加入 `L_total`。

- `L_cls_dark`：学生旧类原始分类 logits 与教师 logits 的置信度加权 MSE；
- `L_box_dark`：学生和教师原始框/分布输出的置信度加权 MSE；
- 教师置信度来自旧类 sigmoid 输出；
- `der_min_confidence` 可过滤过低置信度位置。

默认参数：

| 参数 | 默认值 |
| --- | ---: |
| `der_weight` | 1.0 |
| `der_cls_weight` | 1.0 |
| `der_box_weight` | 0.25 |
| `der_min_confidence` | 0.0 |

经典 DER 通常保存历史样本及其当时 logits；本项目为适应密集检测和存储约束，不持久化大尺寸多尺度 logits，而由冻结的上一阶段教师在线计算 dark target。该变体节省存储并兼容动态均衡回放池，但增加教师前向开销，且知识目标代表“上一阶段模型”而非“样本首次入池时的模型”。对外报告应明确这一差异。

## 13. Sparse-MoE 特征级路由

### 13.1 插入位置与流程

Sparse-MoE 插入 YOLO Detect 头之前，对多尺度特征做残差适配。输入通道从实际模型动态读取，通常对应 P3/P4/P5：

```text
Backbone / Neck 多尺度特征
          │
          ├─ 上下文辅助头：模态 + 场景
          ├─ 图像质量统计
          └─ 共享 Router（每张图一次）
                     │
                   Top-K
                     │
       每尺度稀疏专家残差适配
                     │
                 Detect Head
```

### 13.2 Router 输入与 Top-2

每张图共享一个跨尺度路由结果。Router query 由以下信息拼接：

- 多尺度特征全局池化嵌入；
- stop-gradient 的 IR/SAR 模态概率；
- stop-gradient 的 air/sea/urban/forest 场景概率；
- 输入质量统计：均值、标准差、梯度能量和高频信息。

辅助概率在进入 Router 时停止梯度，避免 Router 反向捷径破坏辅助头的监督语义。

默认 `top_k=2`。Router 先计算全部专家概率，仅执行概率最高的两个专家，并将这两个概率重新归一化为和为 1 的混合权重。因此 Top-2 是“每图动态选择两个专家并加权”，不是两个固定模型投票。

### 13.3 专家结构

每个专家为轻量残差瓶颈：

```text
1×1 降维 → depthwise 3×3 → SiLU → 1×1 升维 → 残差相加
```

最后的升维层零初始化，使新插入专家在训练起点接近恒等映射，减少对已训练检测器的瞬时扰动。

### 13.4 损失函数

```text
L = L_YOLO
  + λ_m   · L_modality
  + λ_s   · L_scene
  + λ_bal · L_balance
  + λ_z   · L_router-z
  + λ_a   · L_anchor
```

DER 同时启用时，再加入 `λ_DER · L_dark`。

| 损失 | 作用 |
| --- | --- |
| `L_modality` | 监督 IR/SAR 上下文头 |
| `L_scene` | 监督四场景上下文头 |
| `L_balance` | 防止样本塌缩到少数专家 |
| `L_router-z` | 控制 Router logits 数值规模 |
| `L_anchor` | 约束专家参数偏离上一阶段 EMA 锚点 |

元数据缺失时对应目标标为 unknown，并在辅助损失中掩码。

### 13.5 默认超参数

| 参数 | 默认值 |
| --- | ---: |
| `expert_count` | 5 |
| `top_k` | 2 |
| `expert_bottleneck` | 0.25 |
| `router_hidden` | 128 |
| `aux_hidden` | 128 |
| `modality_loss_weight` | 0.10 |
| `scene_loss_weight` | 0.10 |
| `balance_loss_weight` | 0.01 |
| `router_z_loss_weight` | 0.001 |
| `anchor_loss_weight` | 0.001 |
| `anchor_rho` | 0.95 |
| `router_temperature_start` | 2.0 |
| `router_temperature_end` | 1.0 |
| `router_temperature_warmup_epochs` | 3 |

温度在 warmup 内从 2.0 降到 1.0，使早期路由更平滑、后期选择更明确；也可通过 `--router-temperature` 固定温度。

### 13.6 专家锚点、统计与加载

每阶段结束后，以 `anchor_rho` 维护专家参数 EMA 锚点，并在下一阶段通过 `L_anchor` 做软约束。该机制不完全冻结旧专家，仍允许适应新数据。

专家统计包括 Top-K 次数/频率、平均概率、路由熵、最大占用率和变异系数。每阶段开始时重新累计；重载 best checkpoint 后会恢复训练期累计状态，避免最终报告被清零。

阶段产物包括：

- `sparse_moe_config.json`；
- `expert_usage.json`；
- `expert_anchors.pt`；
- `context_metadata_summary.json`。

自定义 MoE checkpoint 应使用项目加载器：

```python
from scene_recognition.detector_module.sparse_moe_checkpoint import load_sparse_moe_checkpoint

model = load_sparse_moe_checkpoint("D:/local_models/final_sparse_moe.pt")
```

普通 `YOLO(path)` 不一定能自动重建自定义模块。正式部署前必须对目标 checkpoint 做 Agent 端到端加载验证；若标准加载失败，应为 `TargetDetector` 增加项目加载器或已加载模型注入接口，不能静默退化为 sidecar 标签回退。

## 14. 训练逻辑

### 14.1 场景分类器增量训练

入口：`scene_recognition/route_training/train_scene_router_incremental.py`

流程：

1. 加载已有四场景 YOLOv8n-cls checkpoint；
2. 合并 r1 与 r2 场景样本；
3. 保持 `air/forest/sea/urban` 四输出；
4. 以 224×224、batch 32 微调；
5. 使用 `optimizer=auto`、cosine learning rate、AMP 和固定 seed 42；
6. 保存中间 checkpoint；
7. 在目标检测验证图上检查跨 easy/hard 组错误；
8. 选择 route-safe checkpoint 并导出 ONNX。

```text
epochs=50, patience=10, imgsz=224, batch=32
workers=2, seed=42, deterministic=True
optimizer=auto, cos_lr=True, amp=True
```

同组场景互相误判不改变检测分支，跨组误判才会改变分支，因此 route-safe 指标比普通 Top-1 更适合选模。

### 14.2 easy 六分类增量训练

入口：`scene_recognition/route_training/train_easy_6class_yolov10_incremental.py`

流程：

1. 从四类 YOLOv10n 迁移 checkpoint 开始；
2. 检测头扩展为六类，保留可迁移基础特征；
3. 使用六分类训练图微调；
4. 训练尺寸为 960×960；
5. 选择 `best.pt`；
6. 以 640×640、batch 1、opset 12 导出 easy ONNX。

```text
epochs=50, patience=20, imgsz=960, batch=8
workers=2, seed=42, cos_lr=True, device=0
```

旧类样本与新类样本共同训练，避免仅注入新类导致旧知识快速丢失。

### 14.3 hard 三分类训练

入口：`scene_recognition/route_training/train_hard_3class_yolov8n_corrected.py`

流程：

1. 加载 COCO 预训练 YOLOv8n；
2. 使用森林/城市 hard 数据；
3. 压缩为 `soldier/tank/armored_vehicle` 三类；
4. 使用 960×960 方形训练；
5. 开启 Mosaic、shuffle、AMP 和 cosine learning rate；
6. 最后 10 epoch 关闭 Mosaic；
7. 保存 best/last，并在独立原图验证集上评估；
8. 导出 960×960 hard ONNX。

```text
epochs=150, patience=20, imgsz=960, batch=8
workers=2, seed=42, deterministic=True
optimizer=auto, rect=False, mosaic=1.0
close_mosaic=10, cos_lr=True, amp=True
```

早期 hard 实验曾使用 `rect=True`、关闭 Mosaic 和 shuffle，结果明显变差；修正版恢复有效基线的增强和采样策略。

### 14.4 增量学习与反馈闭环

检测器的四类到六类扩展依赖“旧类样本回放 + 新类别头扩展”。基础版本未加入蒸馏或 EWC，旧类保持主要依赖混合训练数据和稳定微调；多批次 Class-IL 路线进一步提供 ER、在线教师 DER 和可选 Sparse-MoE。

Agent 记录场景预测、场景置信度、最终路由、检测结果、耗时和模型校验信息。人工反馈可写入 replay 清单供后续训练使用。当前 replay 属于训练数据导出机制，尚未实现在线反向传播和自动替换生产模型。

## 16. 指标、选模与结果解释

### 16.1 阶段指标

每批训练后，在该阶段 val 视图上计算：

- 总体 `precision`、`recall`；
- 总体 `mAP@0.5`、`mAP@0.5:0.95`；
- 每个已见类别的两种 mAP。

逐类指标按 Ultralytics 返回的 `ap_class_index` 映射。某类在当前验证阶段无有效样本时写为 `null`，不能以总体均值补齐。

`mAP@0.5` 主要反映是否大体找到目标；`mAP@0.5:0.95` 对 0.50 至 0.95 的十个 IoU 阈值取平均，更严格地衡量定位质量。

### 16.2 持续学习指标

每类记录：

- `first_arrival`：首次进入训练的阶段；
- `final`：最终阶段得分；
- `forgetting = max(history) - final`；
- `BWT = final - first_arrival_score`。

同时计算已见类阶段平均值。forgetting 越小越好；BWT 为负通常表示遗忘，为正表示后续训练对旧类有正迁移。

### 16.3 val/test 隔离

每批仅使用 val 选取 best checkpoint；test 只在最后一批完成后评估一次，不能用于调参、早停或阶段选模。

主要汇总文件：

- `batch_incremental_stage_summary.json`：单阶段指标和产物；
- `batch_incremental_training_summary.json`：全部阶段、逐类矩阵、遗忘、BWT 和最终测试；
- `pipeline_plan.json`：命令、基础 checkpoint、最终模型和汇总路径。

## 18. ONNX 与昇腾 310B 部署

### 18.1 三模型 ONNX 接口

| 模型 | 输入 | 输出 | opset | 用途 |
| --- | --- | --- | ---: | --- |
| scene router | `[1,3,224,224]` | `[1,4]` | 12 | 场景认知 |
| easy detector | `[1,3,640,640]` | `[1,300,6]` | 12 | air/sea |
| hard detector | `[1,3,960,960]` | `[1,7,18900]` | 12 | forest/urban/不确定 |

三个模型均为 batch=1，便于固定内存和静态图优化。部署包还应包含 `route_config.yaml`、类别映射及 SHA-256 校验文件。

### 18.2 昇腾 310B 适配路径

1. 在 x86 环境使用 ONNX checker 验证结构；
2. 使用 CANN `atc` 将 ONNX 转为 OM；
3. 固定 batch=1 和输入 shape；
4. 在 310B 上分别验证 PyTorch、ONNX 与 OM 输出一致性；
5. 将场景路由、预处理、后处理和三个 OM 串成端到端程序；
6. 测量单帧端到端 FPS、峰值内存及各阶段耗时。

当前已完成三模型 ONNX 导出、结构检查、接口定义和 CPU/CUDA 推理封装；OM 转换与 310B 实机 FPS 尚需在具备硬件和 CANN 的环境中完成，不能描述为已实测。

### 18.3 Sparse-MoE 部署边界

普通 Ultralytics YOLO 可按对应版本 API 导出 ONNX；Sparse-MoE 包含自定义模块和动态 Top-K 稀疏执行。当前完成状态是 PyTorch 训练、验证、checkpoint 恢复和 Agent 诊断可用，不代表动态路由 ONNX 或 Ascend OM 已经可用。

正式导出前还需：

1. 明确导出动态 Top-K 还是固定/静态专家组合；
2. 为自定义模块提供独立 export 路径；
3. 使用 ONNX Runtime 对比 PyTorch 的框、类别和路由输出；
4. 验证昇腾算子支持、动态索引和精度漂移；
5. 固化 `names`、输入尺寸、归一化、阈值与 NMS 配置。

## 25. 结论
